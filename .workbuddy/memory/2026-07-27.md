## 审批流死锁 bug 分析（用户 Hachimi 实测 run_command 反复被拒）
用户在 web 端让 Hachimi 删两个文件，run_command(needs_confirm) 被拒 7+ 次死循环、context 撑到 100%。
根因（P0）：agent 循环用构造时 this.onToolApproval（context.ts:128 defaultApprovalHandler = 查 policy 矩阵），不读 per-call options.onToolApproval。
- AgentRunOptions(agent.ts:15) 根本没声明 onToolApproval；executeRun(agent.ts:289-290) 用 this.onToolApproval
- API server 的交互式审批（server.ts:201-225 pendingApprovals+SSE confirm_required+/api/tools/approve）是死代码——传进 runtime.execute 的 options.onToolApproval 被 agent 忽略
- defaultApprovalHandler 对 web/web-sse/desktop/cli 表面查 allow-safe 策略，needs_confirm 直接返回 false，无弹窗、无等待
- 结果：非 TUI 表面 needs_confirm 工具永远无法被批准；W2.2「显式审批 API」端到端不工作
- 加剧因素：无 safe 级文件删除工具（只能靠 run_command）；拒绝不计入熔断（rejection 在 sandbox.execute 前返回）；assistant 幻觉出根本没出现的弹窗
- 修复方向：agent 优先用 per-call onToolApproval；policy 作为是否「提供」交互审批的守卫；补 safe 级 delete_file/write_file；拒绝计入熔断

## 审批流修复（已实施）
- agent.ts：AgentRunOptions 加 onToolApproval 字段；审批门改为 `options?.onToolApproval ?? this.onToolApproval`，让 API server 的 SSE confirm_required + /api/tools/approve 真正生效；tools.execute 也透传 per-call handler
